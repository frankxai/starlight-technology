When it helps: Models that fit entirely in the eGPU's VRAM (documented: ~3x iGPU for an RTX 5080 16GB; 69-121 tok/s on a 96GB card), since only token-sized data crosses the link after load. Also a second device for image generation or small agents while the iGPU holds the big model (inference). When it does not: Models larger than eGPU VRAM or split across iGPU+eGPU: the link bottlenecks (1.6 tok/s overflow case). ## Clustering mini PCs

### llama.cpp RPC

Layer-wise sharding across nodes over TCP; one head node, RPC servers on the others. Official docs call it proof-of-concept, fragile and insecure. Network needs: Low bandwidth (a forum poster saw >20 MB/s use) but latency-sensitive.. Maturity: Experimental; segfaults reported on some quants (Geerling). Fits larger models, does not speed them up.. Windows: Not documented in the RPC README; all community Strix Halo cluster reports found are Linux..
- 2x Ryzen AI Max+ 395, direct USB4 (~9.4 Gbps), Fedora 43, MiniMax-M2.5-REAP-139B: 15.35 tok/s tg
- same, Qwen3.5-397B: 12.6 tok/s tg
- 4x Framework mainboards, 5GbE switch, DeepSeek R1 Q2_K_M: tg ~8.25 tok/s, same as single node; Llama 405B 0.7 tok/s
Sources: [ex-s12](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md), [rv-s23](https://github.com/visorcraft/strix-halo-llm-perf), [ex-s08](https://community.frame.work/t/building-a-two-node-amd-strix-halo-cluster-for-llms-with-llama-cpp-rpc-minimax-m2-glm-4-6/77583), [ex-s11](https://www.jeffgeerling.com/blog/2025/i-clustered-four-framework-mainboards-test-huge-llms)

### vLLM + RCCL tensor parallel (kyuz0 toolbox)

Two-host TP=2 over Ethernet or RDMA/RoCE with a patched RCCL; the repo confirms both were tested on an Ubuntu 24.04 container. Patch details came from a search summary. Network needs: AMD playbook: 10GbE switch, star topology. RDMA guide: Intel E810 100GbE via DAC in the x4 slot with a riser; RDMA latency ~5 us vs 0.07 ms Ethernet.. Maturity: Repo says benchmarks have not been run for the current image; AMD playbook gives no throughput.. Windows: Linux only (Ubuntu container, Fedora host, apt in the playbook)..
- Two Framework mainboards, E810 RDMA, n/a: No tok/s published. Latency 5.23 us (RDMA) vs 74 us (1GbE); bandwidth 50.6 Gbps.
Sources: [ex-s02](https://github.com/kyuz0/amd-strix-halo-vllm-toolboxes), [ex-s04](https://developer.amd.com/playbooks/clustering-rccl), [ex-s10](https://github.com/kyuz0/amd-strix-halo-vllm-toolboxes/blob/main/rdma_cluster/setup_guide.md)

### exo

Auto-discovery distributed inference. Network needs: RDMA over Thunderbolt 5 only on macOS 26.2+.. Maturity: README: Linux is CPU-only, GPU support under development; no AMD/Windows mention.. Windows: None documented..
Sources: [ex-s13](https://github.com/exo-explore/exo)

1M chunks fit easily on 64GB or 128GB beside a 4B embedder (~2.5GB quantized) and a reranker, at roughly 4-6GB of vector memory. 10M chunks at 1024-1536 dims need ~41-57+ GiB for full-precision in-RAM vectors by the vendors' formulas, which leaves little room for a large model on 64GB and a smaller one on 128GB; quantized or on-disk vectors (Qdrant 4-bit ~8x reduction in its example, pgvector halfvec 2x) are the realistic route. Fit is arithmetic from vendor formulas, not a measured co-run benchmark.

- Ingestion embedding competes with the chat model for the same unified memory bandwidth; no measurement found.

- Qwen3-Embedding lets you choose 32-4096 dims (by model), so truncating to 512-768 cuts vector memory proportionally.

- pgvector HNSW builds fast only if the graph fits maintenance_work_mem (README).

## Scale up versus scale out

- Geerling (4 nodes): clustering did not accelerate inference, it only fit larger models; his advice was to scale vertically as much as possible.
- Two-node llama.cpp RPC runs 139B-397B MoE models at 12-15 tok/s (USB4 ~9.4 Gbps), compared with single-node results of 42.7 tok/s (80B-A3B) and 86.1 tok/s (30B-A3B).
- Latency, not bandwidth, limits layer-split clustering; token generation lost ~15% on every link per a community summary (not fully verified).
- vLLM TP=2 on Strix Halo is documented but Linux-only and, for good latency, uses a 100GbE RDMA NIC in a x4 slot; no tok/s published.
- An eGPU adds a fast lane for models that fit its VRAM (~3x iGPU in one source), but splitting across iGPU and eGPU is link-bound and a VRAM overflow is a cliff.
- For a Windows-first buyer: every documented cluster setup (RPC, vLLM, exo) is Linux or macOS, and Windows dGPU+iGPU showed instability in forum reports.
